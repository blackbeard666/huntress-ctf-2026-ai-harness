# metadata-forensics — coverage atlas (as of D19 post-run, 2026-10-19)

What the lane might ask next vs what we can already answer. Grammar is always `Determine <fmt>.<field> for <member>`;
id `dNN-<fmt>-NNN-<fmt>-<field>`; the registry is `lib.meta` (built-ins = verified/speculative, plus
`lib/meta/prebuilt/*.py` speculative modules ranked in `lib/meta/prebuilt/TARGETS.json`). Check what exists with
`python3 -c "import lib.meta as m; print(sorted(k for k in m.known_fields() if k[0]=='<fmt>'))"`.

**Status:** `seen Dn` = GM-verified that day (built-in, verified tier) · `prebuilt <module>` = speculative extractor
registered (gate passed) · `partial` = some sibling fields registered · `gap` = nothing registered (TARGET name given
when one exists but is not built yet).
**Tools:** (I) = installed (`.venv/bin/python` import or on the `source bin/env.sh` PATH), (M) = missing.
In-window extractors may only import the prebuild gate's `ALLOWED_IMPORTS` (`hctf/prebuild.py:112`: stdlib subset +
`pefile elftools capstone Crypto androguard pyzipper lib`) and may NOT call `open()` -- so Evtx / regipy / olefile /
oletools / dnfile / LnkParse3 / lief / cryptography / asn1crypto / dpkt / PIL / `sqlite3` / `mailbox` / `wave` are
worker-only (LLM side) until the allowlist is widened. See gaps `gate-allowlist-*`.
**Likelihood** reasoning: D9-D15 walked Windows binaries/installers/shortcuts/Office (PE -> PE version -> .NET -> MSI
-> LNK -> OOXML); the next steps are most plausibly other Windows DFIR artifacts and legacy-Office/CFB siblings,
plus deeper fields of already-seen families (timed kits are cumulative, D15 added cross-file synthesis).
**D16 turned to e-mail** (`email.message_id` of one `.eml`; flavor "replies, forwards, duplicates, reconstructed
messages ... stable message identities"). PE stayed three days (D9-11) with a deeper field each day, so D17-D19 most
plausibly ask deeper `email.*` fields (In-Reply-To / References / attachments / Received / auth) or a sibling mail
container (MBOX, Outlook MSG), then cross-message threading as a synthesis question. GM fmt word is `email`, not `eml`.
**D17 jumped to audio instead** (`media.primary_audio_codec_name` of one PCM `.wav` -> `pcm_s16le`; id
`d17-audio-001-media-...`: family `audio`, fmt `media`, ffprobe vocabulary). Flavor: "Voice notes have been
transcoded, renamed, and embedded in mail. Determine the actual codecs, connect equivalent recordings, and find the
stream that breaks the sender's story." -> D18-D20 most plausibly: the same `media.*` namespace on OTHER containers/
codecs (renamed `.wav` that is MP3/Ogg-Opus/M4A/AMR -- "actual codecs"), deeper ffprobe stream fields (sample_rate,
channels, duration, bit_rate, format_name, stream count), a multi-stream container where one stream disagrees
("stream that breaks the story": language/creation_time/encoder/codec), audio as a MIME attachment inside `.eml`
("embedded in mail" -- D16 + D17 combined), and a cross-recording equivalence synthesis ("connect equivalent
recordings": same INFO title / correlation id / PCM payload / duration). Video `media.*` (h264 etc.) is the next step
after that. Email fields remain warm (D16 family carries over in every timed kit).
**D17 post-run:** every mode asked only `pcm_s16le` (no transcode delivered); the D17-night prebuild covered the audio
flavor and `media-video-streams`. Lesson: each new family lands under an ABSTRACT fmt word with tool (ffprobe) vocabulary.
**D18 "Frame of Reference" = video** (`media.primary_video_dimensions` of one h264+aac `video-001.mp4` -> `320x180`; id
`d18-video-001-media-...`: same fmt `media`, family `video`). Prebuilt `media_video.py` answered it in the race probe
(~5 s). Flavor: "Clips, previews, and screen recordings have been mixed together. Use stream geometry to identify
originals, crops, and the recording that could not have come from the claimed device." -- none of it was asked; all
geometry sources agreed (stsd = tkhd = SPS, identity matrix, SAR 1:1) in every set. Audio stayed exactly one day deep
(D17 codec only), so the `media` namespace is moving ONE stream property per day. Next plausible (D19-D21): more ffprobe
geometry (`primary_video_codec_name`, rotation/displaymatrix, SAR/DAR, coded vs display size after SPS/clap crop), the
claimed DEVICE (QuickTime mdta make/model/software, `©mak/©mod`, Android keys, handler/encoder/compressor name), stills
asked through `media.*` ("previews": ffprobe opens JPEG/PNG as a 1-stream video -- lib answers `none` today!), a
geometry synthesis (originals vs crops, aspect groups, the impossible-device file), then a NEW abstract namespace
(`image.*`, `archive.*`, `log.*`/`event.*`, `disk.*`).
**D19 "Little Endian on the Prairie" = ELF** (`elf.e_machine_u16_hex` of one `collector-001.elf` -> `0x003e`; id
`d19-elf-001-elf-...`: plain fmt `elf`, family `elf` -- NOT an abstract `binary.*`). Prebuilt `lib.meta` fmt `elf`
answered it in the race probe (~13 s). Same x86-64 LSB ELF64 in every mode/set; the timed kit pools it with the D9 Go PE
and D12 .NET dll. Media stayed exactly ONE field deep per family (audio D17, video D18) and the lane jumped again, so
media is now warm only as carry-over. Flavor: "Linux binaries from several systems have been pooled with Windows
executables and renamed data. Determine architecture directly from the ELF header and rebuild deployment groups." The
pun is EI_DATA byte order. PE stayed THREE days with a deeper header field each day (D9 machine -> D10 entry RVA ->
D11 version resource), so D20-D22 most plausibly: deeper ELF fields under the same `_uNN_hex`/spec-name grammar
(e_entry/e_type/EI_CLASS/EI_DATA/EI_OSABI/e_flags, PT_INTERP, build-id, DT_NEEDED/SONAME/RUNPATH, `.comment`,
NT_GNU_ABI_TAG, section names) on a big-endian or 32-bit ELF ("several systems"), a non-ELF renamed `.elf` -> `none`
("renamed data"), an architecture/deployment-group synthesis across ELF+PE+Mach-O members ("rebuild deployment
groups"), then Mach-O (fat/thin, LC_UUID, codesign) or Linux packaging (deb/rpm/AppImage) as the next family.
